# 改完自检规范（通用核心）

## 目标

每次代码修改后，在**同一轮回复内**完成质量验证：正确、无死代码、lint 达标、受影响 build 通过。若项目根目录存在 `TODO.md`，同步维护待办，形成「完成 → 清理 → 推荐 → 再迭代」闭环。速度优先：日常只做局部验证，交付收口才全量。

## 触发场景

- 刚完成编写/修改，准备回复用户
- 修复 Bug / 重构后
- 用户要求交付 / 全量验收（自检通过 ≠ 提交；git 提交仍须用户指令）
- 任务实质推进了功能 / 债项（无论用户是否提到 TODO）

## 核心原则

- **每轮必做**：不拖到下一轮
- **速度优先**：日常局部 lint + 受影响 build；禁止默认全仓验证
- **规范优先**：lint/build 过了但违反 `AGENTS.md` 也算未通过
- **诚实**：命令写真实结果；未跑的检查不得写成「通过」
- **TODO 保鲜**（仅当存在 `TODO.md`）：完成的删掉，合理的补上，优先级可读

## 全工具补充

- 仅改 Agent 规范文档（`AGENTS.md`、`.agents/**`、工具薄入口、编辑器 rules）：可不跑应用 build，用 `git diff --check`
- 本轮若启动了 dev / docs 长进程：回复前关闭并确认端口释放（若环境允许）

### 通用 skill 维护

#### A. 真源仓（维护 `@142vip/agent-skills` 的 monorepo）

若本轮动过 `workflow` / `code-dev` / `self-check` / `commit`：

1. **只改**包内 `packages/agent-skills/skills/<name>/SKILL.md`（唯一真源）
2. 若误改了 `.agents/skills/` 镜像 → **同一任务回写**包内文件，禁止只改镜像
3. 改了 TS/CLI 时：`pnpm --filter @142vip/agent-skills build`
4. `pnpm exec vip-agent-skills --target .` 刷新镜像；`--check` 防漂移
5. 实质变更 → 按维护者节奏发版（发版是独立动作）

#### B. 下游仓（仅消费本包）

| 禁止 | 应做 |
|------|------|
| 手改已同步的 `workflow` / `code-dev` / `self-check` / `commit` 镜像并提交 | 通用约束变更 → 提 PR / 改动到 **真源仓**对应 skill 文档 |
| 用下游 commit「覆盖」包内容 | 下游 upgrade 包版本后执行 `pnpm exec vip-agent-skills --target .` |

下游**仅可本地维护**：`AGENTS.md` · `business-map` · `.agents/project/*` · 工具薄入口（不被 sync 覆盖）。

`business-map` 仅下游项目本地 skill，不进入上述流程。

## 日常迭代自检（默认）

| 步骤 | 动作 | 要求 |
|------|------|------|
| 1 · 规范抽查 | 对照本仓 `AGENTS.md` 检查改动 | 必做；违规同一轮修 |
| 2 · 死代码清理 | 删未使用 import / 变量 / 函数 / 类型 | 必做（有 `// keep:` 除外） |
| 3 · 局部 Lint | 本仓 lint 命令 + 改动路径 | 路径内零 error；warning 策略从本仓 |
| 4 · 受影响 Build | 只编波及的 app / package | 无编译错误 |
| 5 · 文档同步 | 改了 README / docs 时同步 | 开发中可只局部 lint |
| 6 · TODO 维护 | 见下文「TODO.md 工作流」 | **仅当根目录存在 `TODO.md`** |

### 局部 Lint（常见写法，以本仓为准）

```bash
npx eslint --fix --max-warnings 0 path/to/a.ts path/to/b.vue
```

- 路径：`git status` 或本轮实际改过的源码
- 禁止借机全仓清历史 warning
- 禁止随意 `eslint-disable` 糊弄

### 受影响 Build 映射

**不要写死应用名。** 按优先级读取：

1. `.agents/project/build-map.md`（若存在）
2. 本仓 `AGENTS.md`「常用命令 / 构建」一节
3. 根 `package.json` scripts / turbo filter 约定

原则：

- 只编改动波及的包
- 改了 library 再编依赖它的 app
- 仅样式且 dev HMR 已确认时可暂缓 build；局部 lint 仍必做
- 仅规范/文档无运行时代码：不跑 app build

### 明确禁止

- 禁止每轮默认全仓 lint + 全应用 build
- 禁止未改动也编一遍「以防万一」
- 禁止跳过局部 lint 就回复「已完成」
- 禁止未执行却写「应该会通过」

## TODO.md 工作流（存在才执行）

> **门闩**：仅当仓库根目录（或 `AGENTS.md` 明确指定的路径）存在 `TODO.md` 时启用。
> 没有该文件 → **不要**主动创建（除非用户明确要求建 TODO）。

目的：让用户与 Agent 持续迭代——完成的划掉，缺口被看见，下一批工作有优先级。

### 何时做

| 场景 | 要求 |
|------|------|
| 本轮完成了某功能 / 修了某债 / 关掉某入口 | **必须**从 `TODO.md` 去掉对应未完成项（或等价描述） |
| 本轮推进后发现清晰的后续缺口 | **应**按优先级追加可执行条目（见「推荐质量」） |
| 仅改措辞、无关修复、纯格式 | 可跳过推荐；完成项仍要删 |
| 用户明确说「不要动 TODO」 | 服从，并在回复说明未改 |

### 文档约定（通用；以文件现有结构为准）

1. **只列未完成**：已完成条目删除，不要改成 `[x]` 堆历史（除非本仓 `AGENTS.md` 另有「Done」区约定）
2. **按优先级**：沿用文件已有分级（如 `P0` / `P1` / `P2`，或 高/中/低）；无则：
   - **P0**：阻塞主路径 / 安全 / 数据正确性
   - **P1**：明确产品能力或联调缺口
   - **P2**：工程债、体验、可选增强
3. **可执行**：一条 = 一个可验证动作 + 尽量带路径 / API / 模块线索
4. **规划区**：若文件有「规划要点」类总表，完成/新增主题后**同步改总表**，避免总表与分节打架
5. **元信息**：若文件头有版本/更新日期，有实质变更时更新日期（版本号仅在本仓约定时改）

### 维护步骤（同一轮内）

1. **读**现有 `TODO.md`（及本仓文档约定，若有）
2. **对齐完成项**
   - 本轮已交付的功能、已修的 Bug、已落地的工程项 → **删除**对应条
   - 半完成：改写为剩余工作，或拆成「已不做的删掉 + 剩余新条」
   - 用户明确不做的 → 删除，勿留「不做清单」
3. **推荐后续（质量门槛）**
   依据本轮改动 + 仓库现状（`AGENTS.md`、相关 README、邻近模块、已知半成品），提出 **0～5** 条（宁缺毋滥）：
   - 必须与当前仓库**真实能力缺口**相关，禁止空话（「优化体验」「提升稳定性」单独成条）
   - 禁止重复已有条目（语义重复合并，不堆砌）
   - 禁止把「下一步该问用户的产品决策」伪装成确定 TODO；产品未定的用疑问或标「待确认」
   - 优先：主路径断点、安全、数据一致性、已露出的半截 API/UI、本轮引入的可测后续
   - 插入位置：对上已有 app/模块分节；新主题才新开小节
4. **写回** `TODO.md`，保持原文件风格（标题层级、checkbox、表格）
5. **回复用户时简述**：删了哪些、加了哪些、优先级理由（各 1 行即可）

### 推荐示例（风格）

```markdown
- [ ] 频道页切真实 API：`SITE_PAGE_DATA_MODE=api` + `GET /main-site/{channel}`（`apis/site.api.ts` 仍 mock）
```

```markdown
- [ ] 边界 JSON 推广 `isJsonRecord` 至 `feishu.service.ts`（`site.api` 已试点）
```

### 禁止

| 禁止 | 原因 |
|------|------|
| 无 `TODO.md` 时擅自新建 | 越权；等用户要 |
| 留已完成或明确不做的项 | 污染迭代信号 |
| 一条里塞多个不相关主题 | 无法按优先级推进 |
| 每轮强行凑满 N 条 | 噪音；可为 0 条推荐 |
| 把猜测当事实写进路径 | 误导后续 Agent |
| 用 TODO 替代当面该问的问题 | 决策应先问用户 |

## 交付收口自检（用户要交付/全量验收）

> **自检 ≠ 提交**：本流程只做质量验证，验证通过即交付结果；`git commit` 仍须用户明确指令、**`git push` 由用户手动操作**（见 `commit` skill），不得把「自检通过」当作「可以自动提交」。

在日常自检基础上追加：

1. 对改动路径再跑一遍局部 lint
2. 按本仓约定跑 packages / 各 app / docs 的**交付级**构建
3. 再扫一遍 `TODO.md`：完成项已清、规划与代码一致
4. 检查清单：

| 项 | 要求 |
|----|------|
| 规范合规 | 对照 `AGENTS.md` 关键纪律 |
| Lint | 改动路径达标 |
| Build | 交付脚本 exit 0 |
| 注释 | 模块职责与复杂分支可读 |
| TODO | 存在则已更新；无则跳过 |
| 收尾 | 临时进程/文件清理 | 临时后台进程已 `TaskStop` / `pkill`；端口偏移后已同步 README |
| 端口 | 是否复用已声明端口 | 未擅自偏移到 `+1` 端口（vite / nest 等） |

具体命令组写在 build-map 或 `AGENTS.md`，本 skill 只定义流程。

## 规范抽查要点（通用摘要）

| 检查项 | 规则 |
|--------|------|
| 类型安全 | **禁止 `any`**；慎用 `unknown`（仅边界+立即收窄）；尽最大努力声明类型；少用 `as` |
| Commit trailer | **禁止** IDE/Agent 产品 trailer；用户要求提交时每条 commit 后必跑 `commit` §「Commit 后清 trailer」脚本并抽查 `%B` |
| 通用 skill 镜像 | 下游**禁止**手改已 sync 的通用 skill；改进回写真源包（见 `workflow` / `code-dev`） |
| 命名 / 常量 | 无魔法值；枚举显式字面量；同概念同词；无单字母心理映射 |
| 业务语义命名 | 慎用 `result` / `data` / `info` / `temp` 等空壳词；变量/返回值须贴业务对象 |
| 无意义包装 | 禁止仅透传 lib 的一层函数（如本地 `pathJoin` → `VipNodeJS.pathJoin`）；有组合逻辑再封装；禁止无意义 `buildXxxResult` |
| 布尔收口 | 无中途 `Boolean(x)`；可选布尔用默认参数 / 解构默认 / CLI option 默认值前置处理 |
| 日期 | 无业务路径 `new Date()`；用本仓 `vipDayjs` |
| 方法可见性 | 类方法显式可见性（若本仓要求） |
| async/await | 禁止有害内联 `await` |
| 构造/DI | 参数分行（若本仓要求） |
| 分层 | Service 不直接操作 Req/Res、不乱抛 HTTP 层异常（Nest 类） |
| 死代码 / 注释废码 | 未使用符号已删；不留大段注释掉的旧代码 |
| 传参 | 可选项无值不传；默认参数优于短路 |
| 包复用 | 不重复实现本仓已有能力（优先 `@142vip/*` 等）；直接调用，勿再套同义别名 |
| 包边界 | `@142vip/common` 不引用 `@142vip/utils`；`@142vip/utils` 不引用 `@142vip/common`；`@142vip/vue` 不依赖 `apps/*`；新包先写边界表 |
| 日期/状态码 | 从 `AGENTS.md`，不发明第二套 |
| 日志 | error 含业务上下文，禁止空 `xxx error` |

## 失败处理

- **日常**：修 → 重跑局部 lint → 重跑受影响 build → 再回复
- **交付**：修 → 局部 lint → 交付级全量

不得带 lint 失败或交付 build 失败宣称完成。

## 推荐回复结构

### 日常

```markdown
## 结论
（1～2 句）

## 验证
- <lint 命令> → 结果
- （若有）<build 命令> → 结果

## 变更
- path：说明

## TODO（若本轮维护了 TODO.md）
- 移除：…
- 新增/调整：…（优先级）
```

> 提交：未获用户指令不 commit；**push 由用户手动操作**；用户要求提交时按 `commit` skill 执行。

### 交付

在验证中列出本仓要求的全部交付命令与结果。日常回复勿假装已全量编过。
